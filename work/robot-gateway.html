The robot's gateway to the cloud

One service on every robot sends data up, takes settings down, and serves a small web editor to field engineers.

A simplified, general version of how this works. No company code, customer names or internal details.

The problem

A robot needs one dependable way to send telemetry and reports to the cloud, take new settings back, and let a field engineer adjust it on site, all while WiFi comes and goes and power can be cut at any moment.

How it works

A ROS 2 package on the robot acts as its gateway. Nodes collect telemetry and reports, buffer them locally, and upload in batches when the network is there. A small local API and an embedded web editor let field engineers change maps and sensor settings. Every file the robot depends on is written safely: write a copy, then swap it in, so a power cut never leaves a half written file.

What I built

  • Started the package in 2024 and wrote most of it.
  • The telemetry streamer: buffered, batched uploads to a time series store.
  • The sync of processed reports to the cloud.
  • A web editor for the robot's sensor safety profiles, with checks, version history and restore.

Choices that mattered

  • Buffer, then batch. Robots lose WiFi all the time. Data should wait, not disappear.
  • Safe writes everywhere. Write a copy, then swap it in. A power cut can never corrupt a file the robot needs.
  • History and restore for settings. A bad sensor profile can be rolled back, not rebuilt by hand.
